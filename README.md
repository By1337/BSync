# BSync

BSync — система обмена данными между Paper-серверами. Она состоит из отдельного TCP-сервера и Bukkit-плагина, который подключает игровые серверы к нему. Другие плагины могут использовать BSync для хранения данных игроков, передачи сообщений и публикации событий между подключёнными серверами.

Для данных игроков BSync хранит снимки по UUID и выдаёт блокировку на время работы с игроком. Это позволяет не загружать и не изменять одни и те же данные одновременно на разных игровых серверах. Сообщения для игрока (`mail`) можно сохранить, даже когда он не находится онлайн: они доставляются при следующей загрузке его данных.

## Модули

| Модуль | Назначение |
| --- | --- |
| `bsync-common` | Сетевой протокол, пакеты, каналы и обработка запросов. |
| `bsync-client` | TCP-клиент, повторное подключение, клиентские каналы блокировок и публикаций. |
| `bsync-server` | Отдельный сервер BSync, обработка каналов, консольные команды и загрузка аддонов. |
| `bsync-db` | Доступ к H2, MariaDB или MySQL и репозитории данных. |
| `bsync-bukkit` | Bukkit-плагин, который создаёт подключения, описанные в его конфигурации. |
| `bsync-k2v` | `PlayerDataRepository<T>` и файловое/сетевое хранилища данных игроков. (есть шейд в BLibV2)|

Сервер и клиент общаются через Netty. При подключении клиент подписывает запрос с помощью Ed25519; сервер проверяет подпись по публичному ключу. После авторизации клиент открывает именованные каналы. Встроены каналы блокировок (`default:locks`) и публикаций (`default:publisher`); серверные аддоны могут регистрировать собственные типы каналов.

## Сборка

Нужны JDK 21 и Maven. Серверный модуль собирается под Java 21, остальные модули — под Java 16. Зависимости `dev.by1337` загружаются из репозитория, указанного в `pom.xml`. Для сборки `bsync-k2v` также нужен локальный `bsync-k2v/libs/result.jar`, указанный в его `pom.xml` как системная зависимость.

```bash
mvn package -DskipTests
```

После сборки исполняемый JAR находится в `bsync-server/target/bsync-server-1.3.2.jar`, а Bukkit-плагин — в `bsync-bukkit/target/bsync-bukkit-1.3.2.jar`.

## Запуск выделенного сервера

Запустите сервер из каталога, в котором должны храниться его конфигурация, ключи и локальная база H2:

```bash
java -jar /path/to/bsync-server-1.3.2.jar
```

При первом запуске создаются `config.yml` и `keys.yml`. После создания `keys.yml` перезапустите процесс: публичный ключ из файла загружается при запуске. Поле `private_key` из `keys.yml` понадобится для настройки Bukkit-клиента. Храните этот ключ как секрет.

Пример `config.yml`:

```yaml
port: 8013
database:
  type: h2 # h2, mariadb или mysql
  user: root
  password: password
  host: localhost
  port: 3306
  database: mydatabase
```

Для H2 используются файлы в рабочем каталоге процесса. Для MariaDB и MySQL укажите адрес сервера БД и учётные данные. В консоли BSync доступны команды `uptime`, `metrics` и `stop`.

## Подключение Paper-сервера

Установите BLib и JAR `bsync-bukkit` в каталог `plugins` Paper-сервера. В `plugins/BSync/config.yml` укажите адрес BSync-сервера и его приватный ключ:

```yaml
id: paper-1
workers: 1
netty_threads: 1
servers:
  main:
    group: player_data
    ip: localhost
    port: 8013
    private_key: 'КЛЮЧ_ИЗ_KEYS_YML'
```

`id` — имя клиента в соединении. `main` — локальное имя подключения, которое используется в адресах `server://`. `group` объединяет несколько подключений для адресов `group://`.

## Хранилище данных игроков
(шейд в BLibV2)
`PlayerDataRepository<T>` создаётся плагином-потребителем через `PlayerDataRepository.create(address, plugin, dataManager)`. Адрес определяет, где лежат данные:

`bsync-k2v` самостоятельно обслуживает `local://`, SQLite и прямые MySQL/MariaDB-подключения. Для них не нужны `bsync-common`, `bsync-client` и плагин BSync. SQL требует доступные HikariCP и JDBC-драйвер выбранной БД. Остальные модули BSync требуются только для `server://` и `group://`; сетевые типы преобразуются внутри адаптера и не используются локальной почтой и импортом/экспортом. Формат файлов и дампов при этом сохраняется.

| Адрес | Хранилище |
| --- | --- |
| `local://players` | Существующая папка `./bsync/<имя-плагина>/players`; если её нет — `players` в папке данных плагина. |
| `server://main/players` | Канал `players` на подключении `main`. |
| `group://player_data/players` | Канал `players` на одном из серверов группы `player_data`; выбор сервера определяется UUID. |
| `mysql://host:3306/database/players?user=plugin&password=secret` | Прямое подключение к MySQL, без сервера BSync. |
| `mariadb://host:3306/database/players?user=plugin&password=secret` | Прямое подключение к MariaDB, без сервера BSync. |
| `sqlite://players.db?repository=players` | Локальная SQLite-база `players.db` в папке данных плагина, для одного сервера. |
| `sqlite:///srv/minecraft/players.db?repository=players` | SQLite-база по абсолютному пути. |

`group://` распределяет ключи между серверами группы. Это не репликация: при изменении состава группы распределение UUID может измениться, поэтому вместе с ним потребуется перенести данные.

Прямое MySQL/MariaDB-хранилище использует InnoDB-таблицы `bsync_player_data` и `bsync_player_mailbox`; последний сегмент URI — пространство имён репозитория внутри БД. База должна существовать, таблицы создаются автоматически в фоне. Все игровые серверы с общими данными указывают одну БД и одно имя репозитория. Поддерживаются `ALL`, `ONLY_BLOBS`, `ONLY_MAILBOX`, а также обычные методы импорта и экспорта. HikariCP 7.0.2 объявлен как `provided`: его должен предоставлять BLib/потребитель без relocation пакета `com.zaxxer.hikari`. MySQL/MariaDB/SQLite-драйверы объявлены только для тестов; в runtime их предоставляет окружение потребителя. Классы драйверов задаются явно, без зависимости от обнаружения через JDBC services. Caffeine не требуется.

Пример с настройками по умолчанию:

```text
mariadb://localhost:3306/game/players?user=plugin&password=secret&lease=30s&renew=27s&pool=4&poll=5s&timeout=1s&acquireWait=5s
```

`lease` — срок владения, `renew` — интервал продления, `pool` — размер пула рабочих запросов. Для продлений выделен отдельный пул на одно соединение. Для каждого занятого игрока по умолчанию выполняется один UPDATE примерно раз в 27 секунд; `getUser` и проверка блокировки обращаются только к локальной памяти. Оставшиеся 3 секунды дают запас на ответ БД. Новое состояние собирается в памяти и записывается с объединением обновлений; при Quit финальный snapshot и освобождение lease выполняются одним условным UPDATE. Пустой репозиторий не опрашивает БД о владении или почте.

`poll` — интервал пакетного опроса почты для загруженных игроков, `timeout` — таймаут ожидания соединения/сокета, `acquireWait` — срок повторных попыток захвата занятого игрока. Продолжительности задаются в `s` или `ms`; `renew` обязан оставлять запас минимум `2 * timeout + 500ms` до конца lease. Спецсимволы в логине и пароле кодируются как компоненты URI; также допустимы `user:password@host`. Стандартные диагностические строки конфигурации исключают учётные данные.

SQL проверяет уникальный `owner_token`, возрастающий `owner_epoch` и срок lease по UTC-времени БД при каждой записи, продлении и подтверждении почты. При потере владения локальные данные становятся недоступны, вызывается `DataManager.forceUnlock`, игрок отключается; поздний ответ не восстанавливает старую сессию. Несохранённый snapshot по возможности остаётся в `bsync/<plugin>/sql/<identity>/lost-snapshots` для ручного разбора и не переигрывается поверх нового владельца. При недоступной БД инициализация и исходящая почта повторяются в фоне; вход ограничен `acquireWait`. `close()` ограниченно ожидает финальные записи.

`pushMail` сохраняет сообщение в локальный fsync-журнал до возврата, затем фоновые попытки передают его в SQL. SQL хранит дедупликацию по ID, число ошибок, последнюю ошибку и время повтора. Доставленные записи сохраняют ID и fingerprint без payload. Обработчик вызывается до ACK; при сбое между обработкой и ACK возможен повтор с тем же ID, поэтому внешние эффекты требуют дедупликации обработчиком. Экспорт читает сохранённые snapshots и ожидающую почту прямо из SQL страницами; ещё не принятый БД локальный outbox в него не входит. Выгрузка не является единой транзакционной копией одновременно изменяющегося репозитория.

SQLite предназначен для одного сервера: владение игроком локальное, без TTL, heartbeat и отдельного пула продлений. Файловая блокировка защищает каждую пару «файл БД + repository» от повторного открытия. При перезапуске токены старых сессий сбрасываются после получения этой блокировки, snapshots и очередь почты сохраняются. Параметр `repository` по умолчанию равен `players`; в одном файле можно хранить несколько разных репозиториев. Относительные пути считаются от папки данных плагина. Журнал исходящей почты и recovery-файлы SQLite также хранятся там, в `sql/<identity>/`; старая папка `bsync/` для SQLite не проверяется. Каталоги, файл и таблицы создаются в фоне.

Для SQLite доступны `pool` (по умолчанию `1`), `poll` (`5s`), `timeout` (`1s`, ожидание соединения и занятого writer), `acquireWait` (`5s`). Параметры `lease`/`renew` не принимаются. Включены WAL и `synchronous=FULL`; файл должен находиться на локальной файловой системе. Почта, дедупликация, буферизованный импорт/экспорт и типы `ALL`/`ONLY_BLOBS`/`ONLY_MAILBOX` поддерживаются так же, как для MySQL/MariaDB.

Для своего типа данных реализуйте `DataManager<T>`:

```java
DataManager<String> dataManager = new DataManager<>() {
    @Override
    public String read(byte[] data, UUID key) {
        // null означает, что сохранённых данных для игрока ещё нет.
        return data == null ? "" : new String(data, StandardCharsets.UTF_8);
    }

    @Override
    public byte[] write(String data, UUID key) {
        return data.getBytes(StandardCharsets.UTF_8);
    }

    @Override
    public void acceptMail(String data, String mail, UUID key) {
        // Обработать доставленное сообщение при необходимости.
    }
};

PlayerDataRepository<String> repository =
        PlayerDataRepository.create("server://main/players", plugin, dataManager);
```

Репозиторий сам загружает данные и получает блокировку при входе игрока, сохраняет снимок и снимает блокировку при выходе. `getUser(uuid)` возвращает загруженное значение, `pushSnapshot(uuid, value)` передаёт новое состояние, а `pushMail(uuid, mail)` отправляет сообщение игроку. `loadSnapshot(uuid)` читает последний сохранённый снимок без получения блокировки и возвращает `CompletableFuture<T>`; если снимка нет, результат равен `null`. Сетевой запрос может завершиться ошибкой, например при отсутствии ответа. При выключении плагина вызовите `repository.close()`.

Загрузка при входе выполняется асинхронно. Выбор хука зависит от сервера:

- Форк с `AsyncPlayerDataLoadEvent`: используется это событие.
- Paper 1.21.7+: используется публичный `AsyncPlayerConnectionConfigureEvent`.
- Paper 1.20.6–1.21.6 с Mojang mappings: перед обработкой `ServerboundFinishConfigurationPacket` вход приостанавливается на уровне Netty, данные загружаются в рабочем потоке, затем обработка пакета продолжается. Основной поток сервера и Netty event loop не ожидают блокировку. При ошибке или выключении репозитория ожидающее соединение закрывается.
- Более старые серверы: остаётся `AsyncPlayerPreLoginEvent`. Прямой вход работает, но переход через Velocity может завершиться отказом из-за блокировки на исходном сервере. Этот режим имеет ограниченную поддержку; синхронного ожидания в основном потоке нет.

Проверка хука выполняется по доступным классам, а не по строке версии. Данные не загружаются в pre-login на поддерживаемых Paper с Configuration-протоколом: к моменту захвата блокировки Velocity уже может отключить исходное соединение. Если соединение закрывается до Join, его данные и блокировка освобождаются; поздний ответ отменённой загрузки не восстанавливает игрока в репозитории.

## Гарантии mailbox

`pushMail(UUID, String)` остаётся `void`. Нормальный возврат означает, что сообщение записано в локальный журнал с `fsync`; дальше доставкой занимается библиотека. Запись журнала выполняется синхронно в вызывающем потоке, сеть и серверная БД — асинхронно. Ошибка первичного сохранения (например, заполненный диск) выбрасывается сразу: сообщение не объявляется принятым, если его негде сохранить. После закрытия репозитория новые сообщения не принимаются.

- Отправитель хранит неподтверждённые сообщения в `bsync/mail-outbox/`, переживает отключение и перезапуск, повторяет с тем же UUID без TTL и лимита попыток. Задержка повторов растёт до 60 секунд. После закрытия канала очередь продолжает доставляться при его повторном открытии с той же конфигурацией подключения и именем хранилища.
- Сервер подтверждает приём только после коммита БД. UUID, получатель и SHA-256 содержимого сохраняются вместе с сообщением; повтор не создаёт вторую запись. После обработки остаётся постоянная запись дедупликации, поэтому даже повтор после перезапуска не возвращает сообщение в очередь. Такие записи занимают место в БД и автоматически не удаляются.
- ACK доставки отправляется после успешного возврата `DataManager.acceptMail`. При исключении, отказе или потере ACK сообщение остаётся в БД и повторяется. Неудачи содержат ID, UUID игрока, число попыток и задержку; последняя ошибка доставки и число попыток также сохраняются в БД (`last_error`, `attempts`, `next_attempt`). Ошибка в первом сообщении задерживает следующие сообщения того же игрока.
- `local://` использует тот же файловый журнал: удаление происходит после успешного обработчика; ошибка оставляет сообщение для фонового повтора. Старые `.mailbox`-файлы и серверная SQL-очередь автоматически переносятся с сохранением ожидающих сообщений.

Гарантия — **at-least-once вызов обработчика** при восстановлении доступности и сохранности дисков/БД. Возможен повтор при падении между выполнением обработчика и ACK. Изменения в игровых объектах, сохранение player snapshot и внешние транзакции не образуют общую транзакцию с mailbox. Для операций, которым нужна защита от повторного применения, переопределите совместимый overload `acceptMail(T data, String mail, UUID player, UUID messageId)` и сохраняйте `messageId` вместе с результатом операции. Старые обработчики продолжают работать. Обработчик должен завершить работу до возврата; запуск задачи «на потом» сам по себе не означает успешного исполнения.

Максимальный размер сообщения — 1 MiB в UTF-8. Порядок сохраняется внутри очереди одного отправителя для одного игрока; общего порядка между разными отправителями нет. Runtime-каталог `bsync/` необходимо сохранять при обновлениях. Новый wire-протокол **11** требует совместного обновления выделенного сервера BSync и клиентов; протоколы 8–10 отклоняются, чтобы старый клиент не подтверждал доставку до обработки.

## Импорт и экспорт PlayerDataRepository

```java
repository.exportTo(Path.of("backups/players.bsync"))
        .thenAccept(stats -> getLogger().info("Export: " + stats));

repository.importFrom(Path.of("backups/players.bsync"), 128)
        .thenAccept(stats -> getLogger().info("Import: " + stats));
```

Оба метода асинхронные и возвращают `CompletableFuture<TransferStats>`. `data` и `mails` — число подтверждённых записей, включая уже существующие письма с тем же ID; `locked` — пропущенные занятые игроки, `failed` — остальные неудачные и повреждённые записи. `successful()` возвращает `true`, если пропусков и ошибок нет. Без второго аргумента `importFrom(file)` использует параллелизм 256; допустимы значения 1–256. Колбэки выполняются асинхронно.

Формат файла:

```text
#bsync-transfer 1
#data
<player-uuid> <base64-raw-snapshot>
#mails
<player-uuid> <base64-utf8-mail> <message-uuid>
```

Пустой snapshot или письмо кодируются пустым Base64-полем. При импорте также принимаются двухколоночные строки писем без `message-uuid`: ID вычисляется из SHA-256 всего исходного файла и номера строки. Поэтому повторный импорт **того же неизменённого файла** не создаёт новые письма; одинаковые письма на разных строках остаются разными сообщениями. Экспорт сохраняет исходные ID писем, включая экспорт из одного хранилища и импорт в другое. Обработанные письма не выгружаются; в `local://` сохраняются отдельные квитанции, чтобы повторный импорт не возвращал уже доставленные ID в очередь.

Для `server://` экспорт читает таблицы БД непосредственно на выделенном сервере, включая пользователей, которых нет в кэше. Для `group://` последовательно выгружаются все шарды, а импорт маршрутизируется по UUID в нужный шард. Клиент передаёт каждому узлу `shardCount = N` и его `shardIndex` (с нуля), взятый из того же отсортированного массива серверов, что использует `ServerGroup.route`. Сервер выдаёт только записи, для которых `Math.floorMod(uuid.getMostSignificantBits() ^ uuid.getLeastSignificantBits(), N) == shardIndex`. Для писем используется UUID получателя. Поэтому при общих таблицах записи распределяются между источниками экспорта без дублей; одинаковые письма с разными message ID сохраняются.

Фильтрация выполняется на IO-worker общим Java-хэшем маршрутизатора. Курсор продвигается и через чужие строки; пустая отфильтрованная страница не завершает выгрузку. Для `server://` отправляется `(N = 1, index = 0)`, что выгружает всю физическую таблицу. Если отдельные БД содержат записи, размещённые по старому составу группы, `group://` их отфильтрует по текущему правилу; для полной выгрузки такого узла используйте `server://`. SQL читается через JDBC forward-only streaming и keyset-пагинацию: до 256 записей и 4 MiB на страницу; один большой snapshot может занимать страницу целиком. Перед чтением snapshot-таблицы сбрасываются ожидающие записи её батчера. Ожидающие записи локального outbox, ещё не принятые серверной БД, в серверный экспорт не входят.

Файлы читаются и пишутся через буферы по 64 KiB. Импорт делает два последовательных прохода по файлу (хэш и чтение записей), не загружая файл целиком. Работает скользящее окно до указанного числа запросов и до 16 MiB сырых данных в полёте, плюс одна предварительно прочитанная запись. Записи одного UUID применяются последовательно. Ошибки строк логируются с номером, остальные записи продолжают импортироваться. Временные ошибки запросов повторяются до трёх попыток, занятые игроки сразу учитываются как `locked`.

Snapshot импортируется только после захвата свободного ключа. Резервация удерживается до завершения коммита и не истекает по player-lock таймауту. Старые записи батчера сбрасываются перед импортом, а кэш обновляется после коммита, чтобы отложенная старая запись не затёрла импорт. Экспорт не удаляет данные, импорт заменяет существующий snapshot свободного игрока и добавляет письма с дедупликацией ID. Файл экспорта сначала полностью пишется во временный файл и только после успеха атомарно заменяет целевой файл.

Это перенос сохранённого состояния, а не общая транзакция на всю сеть: для согласованного переноса остановите изменения данных и доставку писем на время выгрузки. Ошибка файла или соединения завершает Future исключением, уже подтверждённая часть импорта сохраняется. При пропусках можно повторить импорт; не редактируйте исходный файл во время операции. Для новых запросов переноса сервер и клиенты должны поддерживать протокол **11**.

## Публикация сообщений и аддоны

`ChannelMaker.createPublisher(...)` создаёт канал публикаций. Сообщение `byte[]`, отправленное через него, сервер пересылает другим клиентам того же канала. Для расширения выделенного сервера можно поместить JAR аддона в каталог `addons`: основной класс должен наследовать `AbstractAddon` и иметь аннотацию `@BSyncAddon`.
